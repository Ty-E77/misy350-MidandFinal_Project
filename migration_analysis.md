## Summary
The app mixes Streamlit UI, data access, validation, and business rules across `app_core.py`, `dashboard.py`, `service.py`, and `data.py`, with many UI pages still holding business/validation logic and global JSON lists acting as the primary datastore. This creates tight coupling, duplicated logic (Agent vs Buyer), fragile session routing, and scaling risks as features/roles grow.

| Current Area | Structural Issue | Why It Can Hurt Maintainability or Scalability | Recommended Refactor Direction | Priority |
|---|---|---|---|---|
| `show_login_page` | UI contains validation, user creation, persistence (JSON save) and session mutation | Mixing validation/persistence in UI makes testing hard and duplicates validation rules; changing auth flow touches UI code | Move auth validation + persistence into `RealEstateService`; UI should only render form + call service methods; keep `data_manager` handling in `data.py` | High |
| `show_main_app_agent` | Heavy UI + business logic (stats, filters, listing management) intermixed; uses global lists | Business rules (counts, filtering, navigation keys) embedded in UI cause duplication and testing difficulty; adding features requires touching UI code | Extract statistics, filtering, and listing-management operations into `RealEstateService`; keep rendering in `RealEstateDashboard` | High |
| `show_main_app_buyer` | Nearly identical structure to agent page with slight variations (duplication) | Duplicated logic increases bug risk and costs to add features or change rules (e.g., booking rules) | Consolidate shared flows (stats, listing browsing) into reusable service functions; parameterize role-specific behavior in UI layer | High |
| `load_json_list` / `save_json_list` | Direct file I/O surfaced at module-level and used across UI/service | Spreads persistence concerns; file failures propagate into UI with no centralized retry/transaction strategy | Encapsulate JSON I/O in `RealEstateData` (already `data_manager`), expose safe read/write APIs and error/warning reporting to service/UI | High |
| `delete_record_with_rollback` / `update_record_with_rollback` | Transactional semantics implemented ad-hoc around JSON saves in service/UI | Simple JSON save/rollback is fragile (partial updates, concurrent runs), duplicate logic for different record types | Keep transactional helpers in `RealEstateService` but move file-level atomicity and error handling into `data.py`; consider write-temp-and-rename for atomic saves | High |
| `navigate_to` / `update_state_and_rerun` / `queue_rerun` / `flush_rerun` | Navigation + rerun helpers scattered; UI and routing tightly coupled to session-state keys | Centralized routing logic is needed; scattered side-effects make it hard to reason about page transitions or to add middleware (auth checks, audit) | Centralize navigation and rerun control inside `RealEstateDashboard`; expose small API to app core; keep session mutation minimal and predictable | Medium |
| `make_key` | UI-specific key construction used in multiple places | UI key conventions leaking into business logic risks breakage if key format changes; hard to test UI-triggered actions | Keep `make_key` as a UI helper in `dashboard.py` or provide a stable service helper; avoid depending on string-format keys in service logic | Low |
| `show_chat_bot` | Chat responses and state mutations implemented in UI layer with simple rule logic | Hard-coded responses and state handling in UI prevents reuse and unit testing; mixing minor business rules in UI | Keep UI rendering here but move response-generation rules and any persistence into service layer or a dedicated `Chat` component | Medium |
| JSON collections `users`, `properties`, `inquiries`, `bookings` (global lists) | In-memory global lists backed by JSON files used app-wide | Concurrency and durability issues (two users running app concurrently will have conflicts); no transactional isolation; tests rely on mutable global state | Treat these as an explicit data layer (encapsulate access via `data_manager`); avoid long-lived mutable globals—use service-provided snapshots and save through service/data APIs | High |
| `st.session_state` design (many keys) | Large, ad-hoc set of session keys (`page`, selected ids, edit ids, `_queued_rerun`, etc.) | Hidden coupling between UI components; hard to reason about state lifecycle, leaks between pages, tests brittle | Define a small, documented session-state model; encapsulate common patterns (current user, current page, transient inputs) with getters/setters in dashboard/service | Medium |
| Routing via `st.session_state["page"]` | Page routing implemented by string keys in session state | String-based routing is fragile, lacks validation, and spreads page-specific logic across modules; adding routes leads to spaghetti conditionals | Introduce a routing layer (enum or registry) in `RealEstateDashboard`/`app_core.py` that maps pages to handlers; keep handlers in UI module | Medium |
| JSON-as-DB simulation (ad-hoc) | Business logic assumes synchronous file saves and no concurrent access; no schema/enforcement | Scaling to multi-user or more complex workflows will expose race conditions, corruption, and inability to run background jobs | For short-term keep JSON but centralize and harden in `data.py` (atomic saves, file locks); long-term plan for a real DB or transactional layer if multi-user concurrency or scale is required | High |
| Areas likely to become hard to extend (roles, features, rules) | Role-specific branching and in-place validation/business rules inside UI code | Adding roles or new workflows requires duplicating UI+logic in multiple places; business rules scattered across UI/service/data | Consolidate business rules in `RealEstateService` and validation in a dedicated validation module; keep UI thin and composable so adding roles is a configuration + small UI wrapper | High |
